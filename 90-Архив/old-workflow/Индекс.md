# Старый workflow: Perplexity + Windsurf (до Claude Code)

> Историческая справка. До перехода на Claude Code разработка велась через связку Perplexity (анализ) + Windsurf/Kimi K2.5 (исполнение) + Telegram (подтверждение опасных действий с телефона). Ничего из этого раздела не актуально как инструкция к действию — только как контекст "почему проект выглядит так, как выглядит".

## Роли в пайплайне

| Участник | Роль | Что делал |
|---|---|---|
| Владелец | Owner/Supervisor | Постановка задач, approve опасных действий |
| Telegram intake-бот | Intake channel | Голос/текст → структурированный `[INTAKE]`-блок |
| Perplexity | Brain/Architect | Root-cause анализ, готовый промт для Windsurf |
| Windsurf (Kimi K2.5) | Executor/Hands | Выполнение промта по шагам, коммиты, "не думает самостоятельно" |
| Telegram approve | Safety gate | Подтверждение push/deploy/install/delete — см. [[10-Раннбуки/telegram-bridge|раннбук моста]] |

```
Владелец (голос/текст) → Telegram intake-бот → [INTAKE]-блок
   → Владелец копирует в Perplexity → root-cause + план + Windsurf-ready промт
   → Владелец вставляет промт в Windsurf → выполнение по шагам
   → опасное действие? → Telegram approve → ✅/❌ → git push / deploy
```

Принципы: Windsurf не анализирует архитектуру сам, если задача помечена `perplexity-reviewed: true`; Perplexity = "компилятор промтов", Windsurf = исполнитель — роли не смешивались; косметические правки и опечатки шли в обход всего пайплайна напрямую в Windsurf.

## Правила для Windsurf (`.windsurf/rules/`, актуальны были на 27.04–30.04.2026)

**00-project.md** — общий процесс: понять → прочитать файлы → предложить план → дождаться подтверждения → выполнить → отчитаться. План обязателен, если задача > 3 файлов или > 50 строк. Правила веток: `web-review`, `mobile-dev3.0`, `backend`, `docs` — **эти имена веток устарели**, актуальные на сегодня — `web`, `mobile`, `backend`, `docs` (см. корневой `CLAUDE.md`). Дизайн-система (тёмная тема, акцент `#f59e0b`, фон `#020617`) — стоит сверить, актуальна ли она до сих пор, при аудите web/mobile.

**01-web.md** — стек React+TS+Vite, JWT в `localStorage` ключ `mm_token` (по факту в текущем коде используется `app-auth-token`/`mm_token` одновременно — см. аудит web), CSS-переменные дизайн-системы, требования по PWA (на момент записи — не реализовано), адаптивность с брейкпоинтами 768/1024px.

**02-mobile.md** — React Navigation, Expo SecureStore для токена, `useTheme()` вместо хардкода цветов, таблица "mobile как источник правды для web" с маппингом экранов (Habits/Tasks — частично перенесены, Calendar/Profile — не созданы на момент записи).

**03-backend.md** — Express + MySQL, чек-лист добавления эндпоинта (роут → JWT middleware → валидация → обновить `AGENTS.md`/`domain.md` → сообщить о необходимости деплоя), правило "не деплоить автоматически — только вручную через SSH владельцем".

**99-tool-safety.md** — правила для самого Windsurf/Cascade по избежанию ошибок в JSON-вызовах инструментов (экранирование, не батчить чтение файлов) — специфично для инструмента, к Claude Code неприменимо.

## Шаблоны промтов (`docs/prompts/`, `docs/templates/`)

Три шаблона (`bugfix.md`, `new-feature.md`, `mobile-to-web.md`) — заготовки текста, которые владелец копировал и заполнял перед вставкой в Perplexity/Windsurf: указать какие файлы прочитать (`AGENTS.md`, нужный `.windsurf/rules/*`), задачу, ограничения, что нельзя трогать. Плюс `templates/intake-message-template.md`, `perplexity-request-template.md`, `windsurf-execution-template.md` — форматы сообщений между этапами пайплайна.

Отдельно `.agent/spec/tasks.md` содержал более компактные версии тех же шаблонов ("Новая фича" / "Багфикс" / "Перенос mobile→web" / "Рефакторинг") с чуть другой структурой полей — по сути дубликат `docs/prompts/*` с вариациями формата.

## Почему это в архиве, а не в правилах

Claude Code читает `CLAUDE.md` и работает в терминале напрямую — весь протокол "промт → вставка в другой инструмент → approve по Telegram" не применим буквально. Но два принципа из этого workflow унесены в [[07-Правила/Правила-агента]] как всё ещё действующие независимо от инструмента: (1) план перед выполнением для задач крупнее нескольких файлов, (2) подтверждение владельца перед опасными операциями (deploy, миграции БД, массовое удаление).
