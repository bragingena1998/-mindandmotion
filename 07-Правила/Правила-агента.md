# Правила работы над Mind & Motion

> Актуальный контракт. Заменяет собой `docs/AGENTS.md` и `.windsurf/rules/*` — те помечены deprecated, см. [[90-Архив/old-workflow/Индекс]]. Корневой `CLAUDE.md` в `E:\ProjectMM` должен указывать сюда как на источник правды для правил/статуса/архитектуры.

## Git

1. Пушить изменения только в свою ветку каждого подмодуля: `backend` → backend, `mobile` → mobile, `web` → web, `docs` → docs (архив), `docs-vault` → vault, `tg-bot` → tg-bot. Актуальные названия веток — см. `CLAUDE.md` в корне (проверялись `git branch --show-current` 2026-07-22).
2. Не переключать ветки подмодулей без явной команды владельца.
3. Не создавать `.save`, `.bak`, `*_copy` и прочие мусорные файлы в рабочих директориях (в mobile уже есть один такой — `TasksScreen.js.save`, см. [[09-Проблемы/Технический-долг-mobile]] — не плодить новые).
4. Один коммит документации = одна завершённая задача, не копить несколько задач в один doc-коммит без явной причины.

## Код

5. Не угадывать структуру файла — всегда читать перед редактированием.
6. Не затирать существующие функции — только добавлять/изменять то, что нужно для задачи.
7. snake_case ↔ camelCase — бэкенд отдаёт snake_case, клиенты используют camelCase с защитными `??`-цепочками (см. [[06-Домен/Сущности]]). Не менять имена полей в БД без синхронизации с обоими клиентами.
8. API-запросы — всегда проверять токен, корректно обрабатывать 401/403.
9. Оптимистичный UI для тогглов/обновлений: мутировать state сразу, откатывать при ошибке API.
10. **Принцип отладки** (закреплён после самого долгого бага в истории проекта — `daysOfWeek`, см. [[08-Решения/daysOfWeek-и-другие-долгие-баги]]): при наличии бэкенда в репозитории — сначала читать его реальный код, а не строить гипотезы на фронтенде.
11. Перед добавлением нового API-эндпоинта — проверять порядок роутов в Express: специфичные пути (`/reorder`, `/:id/archive` и т.п.) должны идти выше `/:id` (см. [[01-Backend/Текущее-состояние]]).
12. Новый защищённый ресурс, привязанный к пользователю через промежуточную сущность (как подзадачи через задачу) — обязательно проверять цепочку владения, не только валидность токена. См. [[09-Проблемы/IDOR-подзадачи]] как пример, где это было упущено.

## Процесс

13. Для задач крупнее нескольких файлов или заметного объёма изменений — сначала предложить план (какие файлы меняются), дождаться подтверждения, затем выполнять по шагам.
14. Подтверждение владельца обязательно перед рискованными операциями: деплой на VPS, SQL-миграции, массовое удаление файлов, force-push. Принцип унаследован от Telegram-approve-gate ([[05-TG-Bot/Текущее-состояние]]), но действует независимо от того, через какой инструмент идёт работа.

## Документация (протокол для vault)

15. После завершённой задачи, затрагивающей архитектуру или статус фичи — обновить соответствующую заметку "Текущее состояние" в `01-Backend`/`02-Mobile`/`03-Web`/`04-Landing`/`05-TG-Bot`.
16. Новое архитектурное решение — новая заметка в `08-Решения` (или дополнение существующей), а не переписывание истории задним числом.
17. Новый обнаруженный баг/технический долг — атомарная заметка в `09-Проблемы` с полями `status`/`platform`/`severity` во frontmatter (см. существующие заметки как образец, например [[09-Проблемы/IDOR-подзадачи]]) — это даёт возможность строить живые дашборды через Dataview/Bases по статусу.
18. Изменение схемы БД — обновить [[06-Домен/Сущности]].
19. Новый раннбук/паттерн деплоя — новая заметка в `10-Раннбуки`.
20. Устаревший протокол `docs/STATUS.md` + `docs/handoffs/*` больше не используется — эта заметка и структура `09-Проблемы`/`08-Решения` заменяют его целиком.
